# Bombim00 Web v1.2.0

The Chrome Web Push button is in Settings. Settings also links to the existing Android APK release. Push subscriptions are private to the selected devices. The Worker sends only to validated Chrome, Safari and Firefox Push endpoints. It keeps delivery history and does not replay unresolved deliveries.

Before releasing, apply the additive D1 migrations `0002_browser_push.sql` and `0003_v2_control_evidence_receipts.sql` to the production Worker database. Store the VAPID public key, private P-256 scalar (base64url), HTTPS contact subject, a random device enrollment code and a separate random receipt secret (at least 32 characters) as Worker secrets named `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_SUBJECT`, `WEB_PUSH_ENROLLMENT` and `WEB_PUSH_RECEIPT_SECRET`. Set the production Pages service binding `CHECKER` to `bombim00-lottery-checker`. Pages Functions route requests through this binding so the Worker can keep its existing Cloudflare Access protection. Share the enrollment code through a private channel. `MAX_DEVICES` is an optional Worker variable that caps enrolled devices; it defaults to 10 and accepts 1–100. Each enrolled device receives every push, so raise it only when the owner wants more devices.

After release, enroll Chrome on Android, tap the test button and close the tab immediately. Verify the system notification and that tapping it opens the results page. `/health` must show no overdue `push_receipts_pending`; the service worker records `received` after displaying a notification and `opened` after a tap. Verify a new scheduled alert or lottery result on the same device, and verify that a previously sent or unresolved result does not repeat. Then retire the old ntfy follow-up automation and secrets. If rollback is needed, revert the release commit through GitHub and leave the additive D1 tables and delivery history in place.
